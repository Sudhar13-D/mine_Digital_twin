# Build Prompt for Antigravity — Mine Subsidence Monitoring Platform ("Mine Manager")

## Context

I have an existing frontend-only prototype generated by Figma Make. It is a complete, working React UI with mock data but **no backend, no database, no real-time ingestion, and no AI model** — everything is simulated in-browser with `setInterval` and hardcoded arrays. Your job is to turn this into a fully working, real-time full-stack application while preserving the existing UI/UX exactly as designed.

## What already exists (do not redesign the UI — wire it up)

**Stack:** React 19 + Vite + TypeScript + Tailwind CSS v4 (no component library, custom-styled).

**File structure:**
```
src/
  App.tsx                 - Root shell: header, nav, sidebar, panel selector, layout, toast, live clock
  types.ts                - SensorNode, Alert, LayerConfig, RiskLevel, NodeStatus, AlertStatus
  data.ts                 - PANELS + INITIAL_NODES + INITIAL_ALERTS (mock data to replace)
  components/
    GISMap.tsx            - Bird's-eye panel map: sensor markers colored by risk, heatmap/pillar/vector layer toggles, click/hover interactions
    CrossSection.tsx       - Side-view geology slice: overburden strata, coal seam, pillars, sensor nodes above pillars, subsidence prediction animation
    ReadingsTable.tsx      - Live sensor values: tilt, vibration, AE, displacement, soil moisture, temp, UWB, crack
    RiskPanel.tsx          - Risk score, anomaly score, confidence %, predicted days-to-failure, alert list, acknowledge actions
    ReportsPage.tsx        - Compliance report generation/export
    SettingsPage.tsx       - Config: thresholds, layers, panel/site management
    HelpPage.tsx           - Documentation/help content
```

**Domain model (from `src/types.ts` and `src/data.ts` — keep these fields, extend as needed):**
```ts
interface SensorNode {
  id: number; label: string; panel: string
  risk: 'LOW' | 'MEDIUM' | 'HIGH'; status: 'online' | 'offline'
  tilt: number; vibration: number; ae: number; displacement: number
  soilMoisture: number; temp: number; uwb: number; crack: number
  lastUpdate: number; gisX: number; gisY: number; csX: number; pillarId: number
  anomalyScore: number; confidence: number; predictionDays: number
}

interface Alert {
  id: string; level: RiskLevel; panel: string; nodeIds: number[]
  timestamp: string; status: 'active' | 'acknowledged' | 'resolved'
  acknowledgedBy?: string; message: string
}
```

There is also a full **987-line UI/UX design specification** at `src/imports/pasted_text/mine-subsidence-ui-ux.md` describing the intended information hierarchy, layout, interactions, color system, and micro-interactions (GIS map behavior, cross-section animation, alert lifecycle, loading/offline states, etc.). **Read this file first and treat it as the authoritative behavioral spec** — implement backend behavior so it satisfies what this document describes (e.g. node pulses red on HIGH alert, alert acknowledgement flow, offline/no-data state, subsidence prediction animation triggers).

## What you need to build

### 1. Backend — Python (FastAPI) + PostgreSQL
- FastAPI service with clean modular structure (routers, models, schemas, services, deps).
- PostgreSQL schema derived from `SensorNode` and `Alert` models above, plus:
  - `panels` table (multi-site/multi-panel support, matches `PANELS` in `data.ts`)
  - `pillars` table (id, geometry/position, mining date, expected failure mode — referenced by `pillarId` in cross-section)
  - `sensor_readings` table: time-series history per node (tilt, vibration, ae, displacement, soilMoisture, temp, uwb, crack, timestamp) — this is what live readings and historical trend charts should read from.
  - `alerts` table matching the `Alert` model, with status lifecycle (active → acknowledged → resolved) and `acknowledgedBy`.
  - `users` table for basic auth (see Auth section).
- Use SQLAlchemy (async) + Alembic for migrations.
- REST endpoints for: panels, nodes (current state + history), alerts (list/acknowledge/resolve), pillars, reports (compliance export), settings/thresholds.

### 2. Real-time ingestion — MQTT + WebSocket
- Run an MQTT broker (e.g. Mosquitto via Docker) that simulated/real sensor nodes publish to, one topic per node (e.g. `mine/{panel}/node/{id}/reading`).
- FastAPI subscribes to MQTT topics via an async MQTT client (e.g. `aiomqtt`/`gmqtt`), on message:
  - Persist the reading to `sensor_readings`.
  - Update the node's current-state row.
  - Run it through the anomaly detection model (see below).
  - If risk level changes or anomaly score crosses threshold, create/update an `Alert` row.
  - Push the update to connected frontend clients over a WebSocket (`/ws/live`) so the UI updates without polling.
- Include a **simulated sensor publisher script** (Python, runs standalone) that publishes realistic fluctuating readings per node to MQTT continuously, so the system is fully demoable without real hardware — model its fluctuation logic on the existing `setInterval` simulation currently in `App.tsx` (small random walk for LOW/MEDIUM nodes, escalating drift for HIGH-risk nodes).
- On the frontend, replace the mock `setInterval` state updates in `App.tsx` with a WebSocket client that receives live node/alert updates and updates React state exactly the way the current mock loop does today (same visual pulse/toast behavior).

### 3. AI/ML anomaly detection
- Implement a lightweight anomaly detection + subsidence prediction service:
  - Input: rolling window of a node's recent readings (tilt, vibration, ae, displacement, crack rate-of-change).
  - Output: `anomalyScore` (0–1), `confidence` (%), `predictionDays` (estimated days to potential failure) — these map directly to existing `SensorNode` fields already rendered in `RiskPanel.tsx`.
  - Start with a statistical/rule-based or lightweight ML model (e.g. isolation forest or an LSTM/GRU over the time-series, whichever is simpler to stand up first) — architect it so the model can be swapped/retrained later without changing the API contract.
  - Expose this as an internal service called from the MQTT ingestion pipeline (per reading) and also as a batch job for full historical re-scoring.

### 4. Authentication
- Basic login only (no roles/permissions yet, per current scope) — email/password with hashed passwords (e.g. `passlib`/bcrypt), JWT-based session tokens, `/auth/login`, `/auth/me`, `/auth/logout` endpoints.
- Frontend: add a login screen gating access to `App.tsx`; store JWT and attach to API/WebSocket auth.
- Structure the user model and auth middleware so role-based access (supervisor/planner/regulator/admin, mentioned in the design spec's "User Roles" section) can be added later without a rewrite.

### 5. Reports & Settings pages
- Wire `ReportsPage.tsx` to a real backend export endpoint that generates a compliance report (PDF or CSV) from actual `alerts` + `sensor_readings` data for a given panel/date range.
- Wire `SettingsPage.tsx` to persist threshold/layer/panel configuration to the database instead of local component state.

### 6. Infrastructure
- Docker Compose setup with services: `frontend` (Vite), `backend` (FastAPI), `postgres`, `mosquitto` (MQTT broker), `sensor-simulator`.
- Environment-based config (`.env`) for DB connection, MQTT broker address, JWT secret.
- Alembic migration for initial schema, seeded with the existing mock data from `src/data.ts` (3 panels, 6 sensor nodes across Panel 1/Panel 2, 3 sample alerts) so the demo looks identical to today's prototype on first run.

## Constraints
- **Do not change the visual design, layout, colors, or component structure** of the existing React components — only replace their data sources (props/hooks) with real API/WebSocket data.
- Keep `types.ts` as the single source of truth for shared types; mirror it in the FastAPI Pydantic schemas field-for-field so no frontend components need prop-shape changes.
- Preserve existing UX behaviors described in `src/imports/pasted_text/mine-subsidence-ui-ux.md` (alert pulse animation, node highlight on update, zoom-to-node on click, offline state, loading state) — these should now be driven by real WebSocket events instead of the mock timer.

## Deliverable
A working `docker-compose up` that starts Postgres, Mosquitto, the FastAPI backend (with live MQTT ingestion + anomaly scoring + WebSocket push), the simulated sensor publisher, and the existing React frontend now fully wired to real data — functionally indistinguishable from the current prototype's UI, but backed by a real database and live pipeline instead of mock timers.
